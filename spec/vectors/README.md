# DKDS version 1 test vectors

This directory contains the test vectors for version 1 of the Domain-Keyed Document Stamp
specification (`../specification.md`). Each vector is a stamp, the conditions under which it is
verified, and the result a conforming verifier must produce.

| File | Content |
|---|---|
| `vectors.json` | The vectors. |
| `vectors.schema.json` | A JSON Schema (draft 2020-12) describing `vectors.json`. |
| `vectors.json.sha256` | The SHA-256 digest of `vectors.json`, in the format of `sha256sum`. |
| `coverage.md` | Each section of the specification with the vectors that test it. Generated. |

The vectors are generated by `../tools/vectors.mjs` and checked against an independent reference
verifier, `../tools/verify.mjs`, by `../tools/run.mjs`.

The vectors are fixed with version 1 of the specification. `vectors.json` changes only to correct an
error, and `vectors.json.sha256` with it; `../tools/check-frozen.mjs` fails on any other change.
`sha256sum -c vectors.json.sha256` checks a copy of the file.

## Contents

The file contains 181 vectors:

| Outcome | Vectors | Examples |
|---|---|---|
| `valid` | 24 | Every maximum size; internationalised domain names; non-Latin text, right-to-left letters and joiners; DNS record variations; CNAMEs with and without DNSSEC |
| `malformed` | 111 | Every Base45 rule, every envelope field, every domain and key ID rule, every payload rule, invalid DEFLATE streams, every range of forbidden code points, invisible characters in names and domains, invalid UTF-8, a decompression bomb |
| `invalid-signature` | 17 | Wrong key, altered data, a signature without the `DKDS` context, and every Ed25519 edge case of section 6.3 |
| `key-not-found` | 20 | Missing, duplicate and malformed key records |
| `unsupported` | 5 | Unknown versions and algorithms |
| `key-revoked` | 2 | Revoked keys |
| `unavailable` | 2 | A failed DNS lookup, directly and through a CNAME |

Where a rule has a limit, there is a vector at the limit that is valid and a vector one step past it
that is not, for example a lookup name of 253 and of 254 characters, and a decompressed payload of
16,384 and of 16,385 bytes.

## Using the vectors

For each vector, a test harness:

1. gives the verifier the string `text`, exactly as a QR scanner would deliver it;
2. sets the verifier's clock to `now` (Unix seconds);
3. answers the verifier's DNS queries from the `dns` object, and records the names queried;
4. compares the outcome with `expected.outcome`, and the names queried with `expected.queries`;
5. for a `valid` outcome, also compares `domain`, `domain_unicode`, `key_id`, `issued_at`, `dnssec`
   and `fields` (names and values, in order).

A verifier passes the vectors when every comparison of steps 4 and 5 succeeds for every vector.
`../tools/run.mjs` is a complete harness of about 50 lines and can serve as a model.

### Simulated DNS

The `dns` object maps a DNS name to what a resolver returns for it:

| `result` | Meaning | The verifier sees |
|---|---|---|
| `answer` | The name exists. `txt` lists its TXT records, each as a list of character strings to be joined without separators. `dnssec` says whether the answer was validated. | the records |
| `cname` | The name is an alias for `target`. | whatever `target` resolves to, with the DNSSEC status of the entry at the end of the chain; a resolver follows the alias |
| `nxdomain` | The name does not exist. | no records |
| `failure` | No answer could be obtained. | a lookup failure |

A name that does not appear in `dns` does not exist. The verifier must query exactly the names in
`expected.queries`: several vectors require that a malformed stamp is rejected without any DNS query
(specification 8.2). The target of a CNAME is resolved by the resolver, not queried by the verifier,
and is not listed.

`failure` stands for every way of not obtaining an answer: a timeout, a server failure, a DNSSEC
validation failure, or two resolvers that disagree (specification 9.2). A harness simulates it with
whatever error its DNS layer produces.

### Intermediate values

Valid vectors, and only valid vectors, carry an `intermediate` object with the envelope, the signed message and the
uncompressed field list in hexadecimal. They are not part of the comparison; they help locate a
fault when a valid vector fails.

## What the vectors do not cover

Some requirements cannot be checked by comparing outputs. They must be tested in another way.

| Requirement | Section | Why |
|---|---|---|
| Reading the QR code | 3.3 | The vectors start from the decoded text. Decoding the image is left to a QR library. |
| How the result is presented | 9.1 | Presentation depends on the form of the verifier and is checked by inspection. |
| Using two resolvers | 9.2 | The vectors model the combined result of the lookup, not the resolvers individually. |
| Lookalike warnings | 9.3 | Warnings are heuristics and never change the outcome. |
| Issuer requirements | 10 | They concern how issuers operate, not what a stamp contains. |

## Ed25519 libraries

Section 6.3 requires checks that many Ed25519 libraries do not perform. When the 17 vectors of
section 6.3 (16 with the outcome `invalid-signature` and one that is valid) were run through two
common forms of verification, both accepted stamps that the specification rejects:

| Vector | Specification | OpenSSL (Node.js 24) | Cofactored (ZIP-215) |
|---|---|---|---|
| `signature-r-identity` | reject | accept | accept |
| `signature-r-mixed-order` | reject | reject | accept |
| `signature-key-identity` | reject | accept | accept |
| `signature-key-non-canonical` | reject | accept | accept |
| `signature-key-order-2` | reject | reject | accept |
| `signature-key-mixed-order-k1` | reject | reject | accept |
| `signature-key-mixed-order-k0` | accept | accept | accept |

All other signature vectors were rejected by all three.

A verifier that relies on such a library alone accepts, among others, a key equal to the identity
point, under which any signature on any message verifies. Only the holder of the domain can publish
such a key, so it does not let an outsider forge a stamp; it does let an issuer later deny having
signed one, which matters wherever stamps must be attributable. An implementation built on such a
library performs the missing checks of section 6.3 itself before calling it.

In the same test, libsodium (libsodium-wrappers 0.7.15) agreed with the specification on all 17
vectors of section 6.3, so a verifier built on libsodium needs no additional checks.

## Test keys

The vectors are signed with two keys whose seeds are published in `vectors.json`: 32 bytes of `0x07`
(the key of Appendix C) and 32 bytes of `0x08`. Anyone can sign with them. They must never be used for
anything other than testing.

## Stability

- A vector's `id` never changes, and the meaning of a vector never changes.
- New vectors may be added. Removing a vector is a change to the specification and is recorded as
  such.
- Generation is deterministic: running the generator twice produces identical files.

## Regenerating

In `../tools`:

```
npm install
npm test
```

`npm test` regenerates `vectors.json` and `coverage.md`, validates the file against the schema, and
runs every vector against the reference verifier.
